## 二、P0：重复明细行绕过数量校验（已实测复现）

### 2.1 问题

`receivePurchase` / `shipSales` / `createPurchaseReturn` / `createSalesReturn` 四个写入口，都用「**从数据库读到的当前快照**」逐行校验数量，然后逐行过账：

- `packages/server/src/modules/purchase/purchase.inbound.ts:57-65`（入库校验 `inTransit = quantity - received_qty - cancelled_qty`）
- `packages/server/src/modules/purchase/purchase.inbound.ts:151-162`（退货校验 `returnable = received_qty - alreadyReturned`）
- `packages/server/src/modules/sales/sales.outbound.ts:55-65`（出库校验 `unshipped = quantity - shipped_qty - cancelled_qty`）
- `packages/server/src/modules/sales/sales.outbound.ts:157-166`（退货校验 `returnable = shipped_qty - alreadyReturned`）

关键点：`quantity - received_qty - ...` 中的 `received_qty` 在整个 `body.lines.map()` 期间**不会变化**（累加发生在过账循环里的 `UPDATE`）。因此同一个 `orderItemId` 在一次请求中出现两次时，**每一行都能独立通过校验**，然后两行都被过账。

各 Zod schema 均未对 `lines` 做唯一性约束：
`packages/shared/src/schemas/purchase.ts:56-84`、`packages/shared/src/schemas/sales.ts:56-84` 中的 `lines: z.array(z.object({ orderItemId, quantity })).min(1)` 是纯数组，无 `.refine()` 去重；全仓 `refine/superRefine` 仅 5 处，均与此无关。

出库与退货路径**部分**缓解（`requested` Map 按 `物料:仓库` 合并后比对物理可用量，见 `sales.outbound.ts:62-73`、`purchase.inbound.ts:159-170`），但该合并只防「库存被扣成负数」，**不防「单据已执行量超过订单量」**。

### 2.2 实测证据

用内存库 + 真实 service 调用复现（脚本已跑完即删）：

```
===== 1) 采购入库：lines 里同一个 orderItemId 提交两次 =====
采购行 quantity=100，在途=100；提交 [{line:1,qty:100},{line:1,qty:100}]
→ 未抛错！status=received，写入流水 2 条
   received_qty = 200 （quantity 应为 100）
   stock_balance = [{"stock_status":"available","quantity":200}]
   purchase_order.status = received

===== 2) 销售出库：lines 里同一个 orderItemId 提交两次 =====
销售行 quantity=100，未出库=100；库存 available=200
→ 未抛错！status=shipped，写入流水 2 条
   shipped_qty = 200 （quantity 应为 100）
   stock_balance = [{"stock_status":"available","quantity":0}]

===== 3) 销售退货：lines 里同一个 orderItemId 提交两次 =====
该行 shipped_qty=100，可退=100；提交 [{line:1,qty:100},{line:1,qty:100}]
→ 未抛错！return_no=SR-20260301-0001，写入流水 2 条
   本行累计退货量 = 200 （可退上限 100）
   stock_balance = [{"stock_status":"available","quantity":200}]

===== 4) 余额 = 流水净额 一致性自检 =====
   不一致行数 = 0
   余额为负的行数 = 0
```

三点结论：

1. **超收入库**：`received_qty = 200 > quantity = 100`，采购单被推进为 `received`，库存凭空多 100。
2. **超量出库**：`shipped_qty = 200 > quantity = 100`。
3. **退货凭空造库存**：对该行只出过 100，却退回 200 → 库存从 0 变 200，**净增 100 单位无来源库存**。这是最严重的一类（退货入库不受「可退量」约束后完全绕过库存守恒）。

### 2.3 为什么测试没能发现

`packages/server/src/test/acceptance.test.ts:164` 断言了「每个 (物料, 仓库, 状态) 余额 = 流水 direction×quantity 之和」，实测该不变量**依然成立**（不一致行数 0）。因为缺陷造成的是「单据执行量超过订单量」，账本与余额两边同时虚增，自洽。全仓无任何用例覆盖「同一请求重复明细行」（grep `duplicate|重复|两次` 仅命中无关用例）。

### 2.4 修复建议

1. **入口去重（最小改动）**：四个 schema 的 `lines` 增加 `.refine()`，对 `orderItemId` 做唯一性校验，重复即 400；或在 service 内先 `Map<orderItemId, SumQty>` 聚合再校验、再逐条过账。
2. **校验改为「请求内累计 + DB 现值」比较**：即校验时用 `dbValue + 本请求已累计量` 与上限比较，这样即使不去重也不会越界。四者建议同时做，前者给出可读报错，后者成为真正的不变量。
3. **DB 层兜底**：见第四节第 4 条（补 `CHECK` 约束），让越界在存储层不可能落库。

## 三、P1：安全与功能缺陷

### 3.1 不安全默认配置，缺少生产 fail-fast（P1）

- `packages/server/src/config/index.ts:39`：`provider: (process.env.AUTH_PROVIDER ?? 'mock')` —— **缺省即 mock**。
- `packages/server/src/modules/auth/auth.service.ts:124-128`：mock 通道首次登录对**任意姓名**自动建号并授予 `sys_admin`（该逻辑只由 `AUTH_PROVIDER=mock` 时注册的 `/api/auth/mock-login` 触发，见 `auth/routes.ts:88-103`，路由本身的开关是正确的）。
- `packages/server/src/config/index.ts:40`：`jwtSecret: process.env.JWT_SECRET ?? 'dev-secret-change-me'` —— 未配置时 JWT 可伪造。
- `packages/server/src/config/index.ts:30`：`host: ... ?? '0.0.0.0'`；`packages/server/src/app.ts:22`：`cors, { origin: true }`（反射任意来源）。

**组合后果**：一次「部署时忘了放 `.env`」的运维失误，就等于在局域网上开放了「用任意姓名自助换取全权限管理员 token」的接口，同时 CORS 对任意站点开放。`.env.example` 默认值也是 `AUTH_PROVIDER=mock`。

**建议**：启动时校验——当 `NODE_ENV=production`（或 `HOST` 非回环）时，若 `AUTH_PROVIDER !== 'dingtalk'`、或 `JWT_SECRET` 仍为默认值、或为 dingtalk 但关键配置为空，则直接抛错拒绝启动。并考虑把 CORS 默认收敛为具体来源白名单。

### 3.2 停用用户 / 角色变更最长 8 小时不生效（P1）

`packages/server/src/plugins/auth.ts:47-59` 的 `requirePermission` 只做两件事：验签 JWT（`request.jwtVerify()`）、检查 `request.user.permissions.includes(code)`。**从不回查数据库**。而 `permissions` 是签发时固化进 token 的（`packages/server/src/modules/auth/routes.ts:32-39`），TTL 默认 8h（`config/index.ts:41`）。

因此：把某用户 `is_active` 置 0、或撤销其角色/权限后，**该用户持有的旧 token 在到期前仍然通过所有 `requirePermission` 校验**，可直接调用写接口。

前端 `/api/auth/me` 会查库（`auth/routes.ts:80-84` → `loadUserAuthInfo` 检查 `is_active`），所以 UI 侧通常会在下次加载时被踢出；但这不是授权边界，直接持 token 调用 API 不受影响。README 已声明「不做 refresh token 与登出黑名单」，属已知取舍，但**停用账号即时生效**通常是必须项。

**建议**：至少对写操作在 `requirePermission` 内做一次轻量查库（校验 `is_active`），或引入 token 版本号 / `jwt_secret` 轮换 / 短 TTL + refresh。

### 3.3 RBAC 提权与自锁（P1）

- `packages/server/src/modules/system/service.ts:202` 的 `setRolePermissions` **不保护 `sys_admin` 角色**（对比同文件 `:186-192` 的 `deleteRole` 显式禁止删除 `sys_admin`）。持 `system.role.manage` 者可以清空 `sys_admin` 的全部权限 → 系统再无人能管理（需改库恢复）；也可以把全部权限授予任意低权角色。
- `setUserRoles` 允许持 `system.user.manage` 者把 `sys_admin` 分配给自己（或他人）→ 单一权限即等价完全控制。

**建议**：`setRolePermissions` 对 `sys_admin` 只读（或仅允许追加不允许删空）；引入「不可自我提权 / 不可移除最后一个管理员」的校验。

### 3.4 401 只清 localStorage、不清 Pinia store → 僵尸会话（P1）

`packages/web/src/api/client.ts:61-63`：

```ts
if (!response.ok || !payload || payload.code !== 0) {
  const message = payload?.message ?? `请求失败（HTTP ${response.status}）`;
  if (response.status === 401) setToken(null);
```

`setToken(null)` 只写 localStorage；store 自己持有一份 `token` ref（`packages/web/src/stores/auth.ts:7` `const token = ref<string | null>(getToken())`），而路由守卫判断的是 store（`packages/web/src/router/index.ts:311` `if (!auth.isLoggedIn)`，`isLoggedIn` 派生自该 ref，见 `stores/auth.ts:11`）。

**后果**：token 过期后，`isLoggedIn` 仍为 `true`、`auth.user` 仍在、菜单与按钮照常显示、不会跳转登录页，而所有请求持续 401 并弹错。只有 `applyToken`/`clear` 会同步 store。

**建议**：401 时调用 `useAuthStore().clear()` 并把路由跳到 `/login?redirect=`（注意避免 store↔client 循环依赖，可用回调注册或事件）。

### 3.5 「保存并确认」按钮权限码错配，必然 403（P1）

`packages/web/src/views/purchase/PurchaseOrderEditView.vue:9`：

```html
<el-button v-permission="PERMISSIONS.purchaseOrderManage" ... @click="save(true)">保存并确认</el-button>
```

而 `save(true)` 在 `:290` 调用 `POST /api/purchase/orders/${id}/confirm`，服务端该路由要求的是**另一个权限码**：`packages/server/src/modules/purchase/routes.ts:28` 定义 `confirm = requirePermission(PERMISSIONS.purchaseOrderConfirm)`，`:58` 挂在该路由上。

**后果**：只拥有 `purchase.order.manage`（无 `confirm`）的用户能看见并点击该按钮，提交后必 403。`packages/web/src/views/sales/SalesOrderEditView.vue:9,290` 与 `packages/server/src/modules/sales/routes.ts:28,58` 完全同构。

列表页/详情页写法是正确的（`PurchaseOrderListView.vue:157` 用 `canConfirm = auth.has(PERMISSIONS.purchaseOrderConfirm)`）。**建议**：该按钮改用 `purchaseOrderConfirm`。

### 3.6 报表导出 CSV 只导出当前页（默认 20 行）（P1）

四个报表导出均调用 `download(PATH, { ...query(), format: 'csv' })` 且不带分页：
`InventoryLedgerView.vue:163`、`StockSnapshotView.vue:159`、`ItemMovementView.vue:206`、`SupplierLeadTimeView.vue:143`。

服务端 CSV 分支发送的是**分页后**的 `list`：`packages/server/src/modules/report/report.routes.ts:27-28` `const { list, page, warnings } = queryInventoryLedger(query); if (query.format === 'csv') return sendCsv(reply, list, ...)`；而 `pageSize` 默认 20（`packages/shared/src/schemas/common.ts:12` `pageSize: ...max(200).default(20)`），并在 service 里落成 SQL `LIMIT/OFFSET`（`report.service.ts:86-88`），供应商提前期则在 JS 里切片（`report.service.ts:318-319`）。

**后果**：用户点「导出 CSV」只得到前 20 条，**静默截断**，对账/汇报场景易出错。**建议**：导出路径绕过分页（或前端显式传大 `pageSize`，并在服务端对导出单独放开上限），或在 CSV 响应头/告警中明确告知截断。

### 3.7 IF-6 默认把 draft/cancelled 订单计入「未出库量」（P1）

`packages/server/src/modules/public-api/public.service.ts:490-495`：只有显式传 `status` 时才过滤；不传则**不做状态过滤**，返回全部订单行，其中 `unshipped = quantity - shipped_qty - cancelled_qty`（`:525`）。

而系统内部对同一概念 `reserved` 的定义是**只统计 `confirmed`/`partial`**（`packages/server/src/modules/inventory/stock.query.ts:130-134`）。

**后果**：下游供应链计划引擎若直接消费 IF-6 且不显式加状态过滤，会把**已取消订单的整行数量**当作待出库需求，系统性高估需求。这是对外接口语义与内部口径的不一致，且默认行为是「多算」。**建议**：默认口径与内部 `reserved` 对齐（默认只返回 `confirmed`/`partial`），或在 `_warnings` 中明确提示，并在 README 的 IF-6 说明中写清默认范围。

### 3.8 明细账与库存现状表对同一状态给出不同金额（P1）

`packages/server/src/modules/inventory/stock.engine.ts:113-117` 的移动加权平均成本在**入库时** `Math.round` 到整数分，出库则沿用这个已舍入的均价（`:109-110,117`）。因此「流水累计价值」与「余额 × 均价」两个口径会分离，而系统里恰好各有一张报表分别使用其中一个：

- 进销存明细账走流水累计：`report.service.ts:105-109` `closing_amount = opening_amount + in_amount - out_amount`。
- 库存现状表走 `数量 × 均价`：`report.service.ts:146` `on_hand_amount: row.on_hand * avgCost`（均价来自 `:135` 的 `MAX(avg_cost)`）。

**这不是理论问题，仓库自带的测试数据就能复现**：`packages/server/src/modules/report/report.test.ts:126-128` 写入 `100 @ 500`、`50 @ 600`、出库 `-30`，得到均价 `round(80000/150) = 533`。

| 口径 | 计算 | 结果 |
| --- | --- | --- |
| 明细账 `closing_amount`（测试断言值，`report.test.ts:144-145`） | 0 + 80000 − 30×533 | **64010** |
| 库存现状表 `on_hand_amount` | 120 × 533 | **63960** |

同一状态、同一天，两张报表相差 50 分且都「算对了自己那一套」。更值得注意的是：**测试把漂移值当作正确值固化了下来**（`report.test.ts:144-145` 断言 `closing_amount: 64010`），而全仓**没有任何用例交叉核对这两张金额报表**。

**建议**：明确金额的唯一权威口径——要么改成「金额不随均价舍入漂移」的记账方式（如出库金额按 `结存价值 × 出库量/结存量` 计算），要么让库存现状表的金额也由流水累计推导；并补一条「明细账期末金额 = 现状表库存金额」的对账用例。此外建议评估把金额改为「按比例分摊的分数/更大精度」（如用厘或按价值池维护）以消除逐笔舍入误差。

## 四、P2：正确性与健壮性

1. **时区口径混用（真实影响 UTC+8 部署）**。`todayIso()` 用 `new Date().toISOString().slice(0,10)` 取「当日」（`packages/server/src/lib/sqlite.ts:18-20`）；`defaultRange` 同法取「本月 1 日 / 今日」（`packages/server/src/modules/report/report.service.ts:27-29`）；`normalizeAsOf` 把 `YYYY-MM-DD` 归一为 **UTC** 当日末刻 `T23:59:59.999Z`（`packages/server/src/modules/inventory/stock.query.ts:79-85`），而业务时间戳由 `new Date().toISOString()` 写入（`stock.engine.ts:105`）。本机时区为 CST（UTC+8），因此**本地 00:00–08:00 之间的操作会被算到前一天**，月度报表的「本月 1 日」边界同样偏移。建议统一按业务时区（或显式接受 UTC 并在文档写明）。

2. **README 对 `as_of` 缺省语义的表述不准确**。README 称「历史时点 `as_of` … 缺省取服务端当日」，但对外 `/inventory` 在不传 `as_of` 时走的是**当前余额**分支（`stock.query.ts:119-125` 的 `as_of ? 重算 : 读 stock_balance`），并非「当日末刻重算」。BOM 接口才真正缺省取当日（`bom.service.ts:93-95`）。

3. **库存金额口径只含 available 桶**。`packages/server/src/modules/report/report.service.ts:146` `on_hand_amount: row.on_hand * avgCost`，而 `on_hand` 按定义只统计 `available` 桶（`stock.query.ts:154`），frozen/qc 不计入。库存现状表的「库存金额」因此系统性低于账面实物价值，列名 `on_hand_amount` 也不易被业务方正确理解。建议增加 `total_amount` 或明确列注释。

4. **数据库层对「执行量 ≤ 订单量」无任何兜底约束**（**已修复**，见第 9 节）。`purchase_order_item.received_qty` / `sales_order_item.shipped_qty` 无 `<= quantity` 约束（`0001_init.sql:189-200`、`:226-236`，仅 `quantity > 0`），所有守恒都靠调用方预检——这正是第二节缺陷能落库的直接原因。已用迁移 `0006_stock_invariants.sql` 的触发器补齐（SQLite 无法 `ALTER` 追加 CHECK，且 `purchase_order_item` / `sales_order_item` 被 `*_return_item.order_item_id` 外键引用，重建表风险高）。
   > **修正**：原报告同时建议给 `stock_balance.quantity` 加 `CHECK (quantity >= 0)`，**经实测该建议不成立**。余额是按「写入顺序」累加的运行值，而 `as_of` 时点口径一律按 `occurred_at` 从 `stock_transaction` 重算，二者刻意解耦；系统明确支持补录早于既有流水的历史单据（`stock.query.test.ts:155-169` 就是「故意乱序写入：先出库后入库」）。此时当前余额会**合法地为负**，故它是业务时点的派生结果而非数据库不变量。给 `stock_balance` 加该触发器会让上述 `as_of` 用例失败（实测 2 项失败），因此**未采纳**。非负性只能由各单据入口按业务意图预检，不能下沉为表级约束。

5. **`cancelled_qty` 是只读的死字段（新增发现）**。全仓搜索确认**没有任何代码路径写入** `purchase_order_item.cancelled_qty` / `sales_order_item.cancelled_qty` / `transfer_order_item.cancelled_qty`：`cancelOrder`（`purchase.service.ts:168-179`、`sales.service.ts` 同名函数）只把表头 `status` 置为 `cancelled`，从不回填行级取消量。但这些字段被大量读取并参与口径计算（`stock.query.ts:134,141` 的 `reserved` / 采购在途、`public.service.ts:255,525` 的 IF-4/IF-6）。后果：列名暗示存在「行级部分取消」，实际不存在；IF-6 的 `unshipped = quantity − shipped_qty − cancelled_qty` 中的 `cancelled_qty` 恒为 0，因此 3.7 节的问题必须靠**状态过滤**解决，而不能指望这个字段。建议要么实现行级取消，要么删除该列以免误导。

6. **移动加权平均成本的整数舍入与 `LIMIT 1` 取值**。每次入库对均价 `Math.round`（`stock.engine.ts:115`），逐笔累计存在舍入漂移；`readWarehouseCost` 用 `LIMIT 1` 从 (物料, 仓) 的**任意一条**状态行取成本（`stock.engine.ts:31-38`），其正确性依赖 `:149-153` 那条 `UPDATE ...
