# P9 · 种子数据 + 验收测试 实施计划

## Context

P0–P8 已把系统从脚手架做到「作业 + 看结果 + 对外接口」的完整闭环：基础资料、库存核心引擎、采购、销售、调拨/盘点/预警、BOM 多版本、对外 9 接口 + OpenAPI、报表 + 看板。共 115 个 vitest 用例、4 个迁移（`0001_init` / `0002_rbac_seed` / `0003_purchase_return` / `0004_sales_return`）。

但系统目前有一处交付空白：**① 新库是空的**——迁移只建表与种 RBAC（`0002` 只种角色/权限/系统参数，无任何业务数据），演示库 `packages/server/data/erp.db` 里的数据是历次浏览器验收手工产生、零散且不自洽（2 物料 / 2 仓库 / 4 采购单 / 2 销售单…），无法支撑报表与看板的完整展示；**② 缺少一次「全链路一起跑」的验收测试**——现有 115 个用例按模块切分，没有一条把「主数据 → 采购入库 → 销售出库 → 退货 → 调拨 → 盘点 → 预警 → 报表 → 看板 → 对外接口」串起来的端到端验收。

P9 补齐这两点，**不新增表、不新增迁移、不改业务逻辑**。

### 已与用户确认的范围决策

1. **种子数据落点 = 独立 seed 脚本 + `pnpm seed`**：新增 `packages/server/src/db/seed.ts` 与 CLI 入口，**不写进迁移**（避免把演示业务数据带进任意新库/生产库）。复用既有 service 灌业务单据；主数据（分类/物料/仓库/往来单位/BOM）因无 service 层，用参数化 INSERT（与既有 route 内联 SQL 等价）写入。
2. **验收测试形态 = 后端 E2E 验收测试文件**：新增 `src/test/acceptance.test.ts`，在 `:memory:` 库上跑 seed 后，逐项断言各阶段交付物（一条命令完成端到端验收）。
3. **演示库处理 = 用 seed 重建**：实现后对 `packages/server/data/erp.db` 执行 `--reset` 清空业务数据并灌入规范演示数据（**保留 `sys_*` 全部系统/RBAC/用户数据**）。
4. **种子范围 = 全量演示数据**：分类 / 物料 / 工厂仓库 / 往来单位 / BOM（多版本）/ 期初库存 / 采购（含入库、退货）/ 销售（含出库、退货）/ 调拨（含在途）/ 盘点（含差异）/ 预警规则，使报表与看板所有板块均有数据。

## 关键口径（必须严格遵守）

1. **零迁移**：P9 不改 `src/migrations/*`，`pnpm migrate` 输出保持「已跳过（已应用）：0001–0004」。种子数据只由 `pnpm seed` 显式触发。
2. **可重复执行（幂等）**：以 `sys_param` 键 `demo_seed`（值 = 首次灌入的 ISO 时间戳）作为标记。标记存在且未加 `--reset` → 打印「演示数据已存在，跳过」并退出 0，**不改动任何数据**。
3. **`--reset` 语义**：仅清空**业务数据**（流水 / 余额 / 各类单据与表体 / BOM / 预警规则 / 认证关联 / 主数据 / `doc_sequence` / `export_task` / 种子标记），**保留全部 `sys_*`**（角色、权限、角色权限、系统参数、`sys_holiday`、`sys_user`、`sys_user_role`）。删除顺序按外键依赖从子到父；删除 `warehouse` 前先 `UPDATE warehouse SET parent_id = NULL`（自引用外键）。整段包在一个事务里。
4. **复用既有 service**：业务单据一律调用导出函数，不手写业务 SQL，保证与线上同一条代码路径：
   - 期初库存 / 盘盈亏 → `postMovement`（`stock.engine`，`bizType='adjust'`）
   - 采购 → `createOrder` / `confirmOrder`（`purchase.service`）+ `receivePurchase` / `createPurchaseReturn`（`purchase.inbound`）
   - 销售 → `createOrder` / `confirmOrder`（`sales.service`）+ `shipSales` / `createSalesReturn`（`sales.outbound`）
   - 调拨 → `createTransfer` / `confirmTransfer` / `shipTransfer` / `receiveTransfer`（`transfer.service`）
   - 盘点 → `createStocktake` / `postStocktake`（`stocktake.service`）
   - 预警 → `createAlertRule`（`alert.service`）
   - 状态转移 → `changeStockStatus`（`stock.engine`）
   - 主数据（分类/物料/仓库/往来/BOM/认证）→ 参数化 `INSERT`（无 service 层）
5. **时间可控**：单据日期用「今日 − N 天」生成，出入库/发货/收货/过账的 `occurredAt` 显式传入，使流水落在近 30 天内且趋势图有多个非零日。
6. **不改业务代码**：P9 只新增 seed 与验收测试文件、改两个 `package.json`、改 `README.md`；不动 `app.ts` / 任何 route / service / schema。

## 风险与注意

- **演示库重建是不可逆操作**：`--reset` 会清空 `erp.db` 业务数据（保留 `sys_*` 与登录账号）。实现阶段由我执行一次并核对计数；如需保留旧数据，可在执行前备份 `erp.db`。
- **单据编号**：`nextDocNo` 依据单据日期生成编号（如 `PO-2026xxxx-0001`），`--reset` 同时清 `doc_sequence` 使编号从 0001 起重排。
- **留痕**：验收测试与 seed 均走既有 service，业务逻辑零改动；若某步失败，外层事务整体回滚，不会留下半截演示数据。
