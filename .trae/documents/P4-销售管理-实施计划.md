# P4 · 销售管理 实施计划

## Context

P3 交付了**第一个真正的单据模块**（采购管理），确立了本仓库的单据模式：表头 + 表体、派生式状态机（不落冗余字段）、行级过账（不新增中间单据表）、`doc_sequence` 单号序列、`postMovement` 同事务组合「写流水 → 累加已执行量 → 推进状态」。P4 销售管理**完全照搬这套模式**，把业务方向从「入」翻转为「出」。

现状盘点（已核实）：

- `sales_order` / `sales_order_item` 在 P0 的 `0001_init.sql`（L206-L241）**已建好**，字段与 `purchase_order*` 对称：表体用 `shipped_qty`（对应采购的 `received_qty`）、`cancelled_qty`，交期字段名为 `due_date`（对应 `promised_date`）。
- 销售权限码 `sales.order.view` / `sales.order.manage` / `sales.order.confirm` / `sales.outbound.manage` 已在 `0002_rbac_seed.sql` 种好，`salesperson` 角色已获授权（含 view/manage/confirm/outbound）。**本阶段不新增权限码、不改种子。**
- 库存查询的 `reserved` 口径（`stock.query.ts` L123-L129）已是 `SUM(quantity − shipped_qty − cancelled_qty) WHERE status IN ('confirmed','partial')`——**出库累加 `shipped_qty` 会自动减少 `reserved`，库存侧无需任何改动**。
- 没有任何 `sales_return` 表 → 需新增 `0004_sales_return.sql`（对应 P3 的 0003）。
- `stock_transaction.biz_type` 的 CHECK 已含 `sale_out` / `sale_return`，无需改。

**与采购的关键不对称**（务必注意）：采购入库是入、采购退货是出；销售出库是出、销售退货是入。而引擎的成本路径按方向分叉（`stock.engine.ts` L109-L117）：**出库自动按当前移动加权平均结转（`unitCost` 被忽略）；入库按 `unitCost` 重算均价，缺省 fallback 为 0**。因此 P3 的采购退货（出库）无需供价，而 P4 的销售退货（入库）**必须显式传入当前均价**，否则会把均价稀释为 0。

已与用户确认的三项范围决策：

1. 销售出库采用**行级直接出库**：不新增发货单表，在销售单行上执行本次出库数量。
2. **销售退货纳入 P4**：新增 `sales_return` 表头 + 表体，按已出库数量退货并即时过账。
3. 销售单**确认时不校验库存**，仅在**出库时**校验物理可用量充足。

## 核心算法与业务规则

### 1. 销售单状态机（只能由业务动作推进）

```
draft ──确认──→ confirmed ──(部分出库)──→ partial ──(全部出库)──→ shipped
  │                 │
  └──取消───────────┴──→ cancelled
```

- **不提供「直接改状态」的接口**，只有 `confirm` / `cancel` / `outbound` 三个动作能推进状态。
- `draft`：表头表体可改、可删除、可确认、可取消。
- `confirmed` / `partial`：表头表体**不可改**，可继续出库，可取消。
- `shipped` / `cancelled`：终态，不可出库、不可取消。
- **取消已确认单据后，其预占数量必须从 `reserved` 中消失**——由「`reserved` 只统计 `confirmed`/`partial`」自动成立，无需额外清理。

### 2. 预占（reserved）是派生量，不落字段

```
销售预占(行) = quantity − shipped_qty − cancelled_qty
销售预占(整) = Σ 行预占，仅当 sales_order.status ∈ ('confirmed','partial')
```

- `shipped_qty` 是唯一需要落库的累加量（出库动作推进）；`cancelled_qty` P4 保持 0（不做行级取消）。
- **确认不校验库存（决策 3）**：确认只推进状态，预占是软占用；库存不足由出库环节兜底。
- **出库校验的是「物理可用量」，不是「净可用量」**：出库前置校验取 `stock_balance` 中 `stock_status='available'` 的桶（`readBalanceByStatus`），而**不是**库存查询页展示的 `available = on_hand − reserved`。否则单据自身的预占会把自己挡在门外。二者用途不同：前者是「仓里实际能发的货」，后者是「可承诺量 ATP」。
- 因此预占遵循**先到先得**：已确认不排队锁定，出库时按物理库存判定。

### 3. 出库动作（行级直接出库）

一次出库请求携带一单的多行数量，整个请求在**一个事务**内完成：

1. 校验单据状态 ∈ (`confirmed`, `partial`)，否则 409
2. 逐行校验 `本次数量 ≤ quantity − shipped_qty − cancelled_qty`，否则 409
3. **按 (物料, 仓库) 合并请求量**，逐组校验物理可用量 `readBalanceByStatus(...).available ≥ 合并出库量`，否则 409
   —— **引擎出库分支不校验库存**（`postMovement` 只校验 `quantity > 0`，出库走 `recalcCost=false` 分支不读数量），会写出负库存，**必须由 service 预检兜底**
4. 逐行调用 `postMovement({ bizType: 'sale_out', bizId, bizNo, direction: -1, stockStatus: 'available', quantity })`
   —— **不传 `unitCost`**，引擎按当前移动加权平均自动结转出库成本
5. 逐行 `UPDATE sales_order_item SET shipped_qty = shipped_qty + ?`
6. 重新计算整单状态：全部行 `shipped_qty + cancelled_qty ≥ quantity` → `shipped`；否则任一行 `shipped_qty > 0` → `partial`
7. 更新表头 `updated_at`

出库数量允许小于未出库量（分批发货）；每行独立，一次可只发一部分行。

### 4. 销售退货

退货以「已出库的销售单行」为源，**创建即过账**（无草稿态），整个请求一个事务：

1. 校验单据状态 ∈ (`confirmed`, `partial`, `shipped`)（草稿单没有可退的货）
2. 逐行校验 `退货量 ≤ shipped_qty − 已退货量`，其中**已退货量不落字段**，实时从 `sales_return_item` 按 `order_item_id` 求和 —— 与「预占不落字段」同一原则
3. 逐行取 `unitCost = readWarehouseCost(db, productId, warehouseId)`（退货前当前均价），调用
   `postMovement({ bizType: 'sale_return', bizId, bizNo, direction: +1, stockStatus: 'available', quantity, unitCost })`
   —— **必须显式传 `unitCost`**：传给引擎的当前均价满足 `avgCost = (qtyBefore*costBefore + qty*costBefore)/(qtyBefore+qty) ≡ costBefore`，**均价零漂移**；缺省会按 0 入库稀释均价
   —— 与采购退货（出库、自动结转）**不对称**，此处为入库、需显式供价
4. 写 `sales_return` 表头 + `sales_return_item` 表体（`unit_cost` 取步骤 3 的 `unitCost`，`amount = quantity × unit_cost`），单号 `SR-YYYYMMDD-NNNN`
5. 回写表头 `total_amount`
6. **退货不改变销售单状态**（已 `shipped` 的单退货后仍是 `shipped`）

销售退货不涉及收款 / 发票 / 应收核算（不在本阶段范围）。

### 5. 单号序列

复用 P3 的 `packages/server/src/lib/doc-no.ts`：

```ts
nextDocNo(db, docType: DocType, bizDate: string): string
// INSERT INTO doc_sequence(doc_type, biz_date, next_no) VALUES (?, ?, 1)
//   ON CONFLICT(doc_type, biz_date) DO UPDATE SET next_no = next_no + 1
// → 读回 next_no → `${前缀}-${YYYYMMDD}-${补零 4 位}`
```

`DOC_TYPE_PREFIX` 增 `sales_return: 'SR'`（**不复用 `SO`**，否则与销售单序列撞号；且 `DocType` 缺该键会导致 TS 编译失败）。

### 6. 金额与数量

- `amount = quantity × unit_price`（分），`total_amount = Σ amount`，整数运算，展示层才做除法
- 数量为最小单位整数；`qty_precision > 0` 的物料仅影响前端展示
- 所有写操作包在 `db.transaction()` 内；`postMovement` 自带事务，better-sqlite3 嵌套自动降级为 SAVEPOINT

## 单元测试（镜像 P3）

`packages/server/src/modules/sales/sales.test.ts`，用 `createTestDb()` + `seedFixtures(db)`（复用 `CU-01` 客户 / `RM-001` / `FG-001` / `WH-01`）：

1. **单号序列**：同日两张单为 `SO-YYYYMMDD-0001` / `0002`，跨日重新从 `0001` 起
2. **新建草稿**：`status = draft`，`total_amount = Σ(quantity × unit_price)`
3. **状态机边界**：`draft` 直接出库 → 409；`confirmed` 改表体 → 409；`shipped` 再次出库 → 409
4. **完整链路**：先入库造库存 → 新建 100 → 确认 → 出库 60 ⇒ `reserved = 40`、`status = partial`、`on_hand` 减 60 → 出库 40 ⇒ `reserved = 0`、`status = shipped`、再减 40
5. **取消单据**：`confirmed` 单取消后，`reserved` 统计中其数量消失
6. **超量出库**：`本次数量 > quantity − shipped_qty` → 409，且 `shipped_qty` 与库存均无变化
7. **可用量不足出库**：物理可用量 < 出库量 → 409，库存无变化（决策 3 的兜底）
8. **事务完整性**：一次出库传两行，第 2 行超量抛错 ⇒ 第 1 行的流水、余额、`shipped_qty` 全部回滚
9. **销售退货**：出库 100 后退 30 ⇒ `on_hand` +30、流水 `biz_type = sale_return` 且 `direction = 1`、`unit_cost` = 退货前均价、**退货后均价不变**；退货量为 0 或超可退量 → 409
10. **退货不改单据状态**：`shipped` 单退货后仍为 `shipped`
11. **流水与余额恒等**：`SUM(quantity × direction)` ≡ `stock_balance.quantity`（出库 + 退货后仍成立）
