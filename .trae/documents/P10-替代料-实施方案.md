## 一、附件与本项目的差异（必须先对齐）

附件是面向 **MySQL / PostgreSQL + 有生产工单 / MRP / Redis** 的设计，本项目是 **SQLite + 单进程 Fastify + 无生产工单**。直接照搬会落在没有宿主能力的地方，故先明确差异：

| 附件的假设 | 本项目实际情况 | 本方案处理 |
| --- | --- | --- |
| `mat_` 前缀、`bigint AUTO_INCREMENT`、`decimal(16,3)` 数量 | 无前缀、`INTEGER PRIMARY KEY AUTOINCREMENT`、**数量一律 INTEGER**（`CHECK (quantity > 0)`、zod `.int()`、`postMovement` 强制 `Number.isInteger`；`qty_precision` 字段存在但写入侧仍要求整数） | 表名/主键/时间戳按本项目风格；**替代比例与分配数量必须适配整数**（见 §6.3 与决策 1） |
| 有**生产工单领料**替代 | 本项目**没有生产工单**，也没有 MRP | 不做；本期场景收敛为「销售出库替代」+「需求建议（只读）」（见 §3） |
| **MRP 净需求**自动适配 | 无 MRP 模块 | 不做；改为对下游计划引擎**只读暴露**（IF-9，见 §7.4） |
| **采购申请单** | 无采购申请，采购直接落 `purchase_order` | 降级为「替代料采购建议」，不新增单据（见 §7.3） |
| **Redis 分布式锁**防超配 | 单进程 + better-sqlite3 同步 API + `db.transaction` | 不引入 Redis；改为「规划只读 + 执行与过账同一事务内重算」（见 §6.5） |
| `delete_id` 软删除规避唯一键撞键 | 本项目无软删除先例；`stock_alert_rule` 的 NULL 唯一性是**先查后写**（`assertUnique`），停用走 `is_active` | 沿用本项目先例：硬删除 + 先查后写；停用走 `is_active`（见决策 11） |
| `mat_substitute_customer_forbid` 客户级**禁用**表 | 已存在 `item_customer_certification`（`item_id × customer_id + certified_at/expire_at`，已 seed、已有编辑入口 `PUT /api/masterdata/items/:id/certifications`，但**未参与任何校验**） | **已确认（决策 3）**：复用为**正向认证**（default-deny 且更贴合规），**不新增**负向禁用表 |
| 质检报告**附件**地址 | 本项目**没有任何文件上传/存储能力** | 无法承载；审批只做「状态 + 审批人 + 意见」文本（见决策 7） |
| 窗口函数取数 | SQLite 3.53.2，**支持窗口函数**（已实测 `row_number() over()` 可用） | 可直接采用附件的「专属仓优先 + 优先级排序」思路，SQL 改 SQLite 方言 |
| 新增 `biz_type` 区分替代出入库 | `stock_transaction.biz_type` 是 **CHECK 枚举（8 值）**，SQLite **无法 ALTER 修改 CHECK**；而该表是不可变核心账本，重建表风险高 | **不新增 `biz_type`**：库存流水复用 `sale_out` / `purchase_in`，替代语义记入独立的 `item_substitute_log`（见 §5.4） |

`item_category.capacity_group`（「产能归类」，UI 可维护、**从未参与任何逻辑**）可作为替代候选的辅助提示，但不作为替代关系的判定依据（替代关系由 `item_substitute` 显式维护，见 §4.1）。

## 二、术语（领域模型 · 供确认后写入 `CONTEXT.md`）

| 术语 | 拟定义 | 易混点 |
| --- | --- | --- |
| **主料** main item | 需求原始指向的物料（BOM 子件、销售订单行上的物料） | 与「父件」不同：父件是 BOM 上层 |
| **替代料** substitute item | 经准入、可在指定范围内顶替主料的物料 | 与「同物料不同批次」无关（本项目无批次表） |
| **替代关系** substitute relation | 「主料 → 替代料」的一条可用规则，携带优先级、替代比例、适用仓、场景、生效期、状态 | 一律**单向**；双向互替需两条记录（见决策 5） |
| **替代比例** replace ratio | 主料需求换算为替代料需求的系数，以**整数分子/分母**表达：`替代料用量 = ceil(主料缺口 × ratio_num / ratio_den)` | **已确认（决策 1）**：不采用附件的小数 `decimal(10,3)`；本项目全链路数量为整数 |
| **替代策略** strategy | `proportion` 按比例混用 / `whole_batch` 整批全量 / `manual` 手工指定 | 附件称"按比例混用（默认）" |
| **场景** scene | 该关系允许生效的业务场景：`sales_out` / `bom_plan` / `purchase_hint` | 附件有 4 个场景，其中 2 个本项目无宿主 |
| **建议** plan | 「按规则算出该用哪些料、各用多少」的**纯计算结果**，不写任何数据 | 与「执行」严格分离 |
| **执行** execution | 真正扣减替代料库存、写流水与追溯日志 | 必须与过账同一事务 |
| **一层不嵌套** | 匹配只查「主料的直接替代料」，不递归查「替代料的替代料」 | 附件的硬性边界 |

> 术语确认后我会在仓库根新增 `CONTEXT.md`（当前仓库没有该文件），只放词汇表与边界，不放实现细节。

## 三、范围划分

### 本期（P10）

1. **替代关系主数据**：增删改查 + 启停 + 生效期 + 优先级 + 比例 + 场景 + 适用仓。
2. **规划模块（深度模块，只读）**：给定主料/仓/需求量/场景/客户，返回分配建议、缺口、跳过原因。**不写库**。
3. **销售出库替代执行**：`shipSales` 支持按建议（或手工指定）用替代料出库，同一事务内重算并过账，写追溯日志。
4. **需求建议（只读）**：BOM 展开页与对外接口可按替代料补齐缺口（不改 BOM 主数据）。
5. **对外接口**（**已确认，决策 9**）：`IF-8 GET /api/v1/substitutes`（替代关系）、`IF-9 GET /api/v1/substitution-plan`（分配建议）——本项目定位是"供应链计划数据底座"，替代对下游净需求至关重要。
6. **报表**：替代料调用统计（含"最近调用时间"，支撑呆滞判断）。

### 后续（不在本期，需先具备前置能力）

- 替代关系**准入审批单**（需附件能力，见决策 7）。
- 生产工单领料替代（需先有生产工单）。
- MRP 净需求自动适配（需先有 MRP）。
- 多对多互替的循环检测（本期只做单向 + 一层）。

### 明确不做

- 不做 Redis / 分布式锁（架构不匹配）。
- 不做质检报告附件（无存储能力）。
- 不改 BOM 主数据来"表达"替代（替代是独立关系，不污染 BOM 版本语义）。
- 不新增 `stock_transaction.biz_type` 枚举值（见 §1 技术约束）。
- 不把替代料写进 `sales_order_item.product_id`（保持订单行"客户订的是什么"不变，替代只落在执行与日志上）。

## 四、数据模型

### 4.1 `item_substitute`（替代关系主表）

```sql
-- 0008_item_substitute.sql
CREATE TABLE item_substitute (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  main_item_id   INTEGER NOT NULL REFERENCES item (id),
  sub_item_id    INTEGER NOT NULL REFERENCES item (id),
  -- 父件语境：NULL = 通用替代（不限定 BOM 上级）；非空 = 仅在该父件下可用
  parent_item_id INTEGER REFERENCES item (id),
  -- 适用仓：NULL = 全仓通用；非空 = 仅该仓
  warehouse_id   INTEGER REFERENCES warehouse (id),
  priority       INTEGER NOT NULL DEFAULT 1 CHECK (priority > 0),
  -- 替代比例：替代料用量 = ceil(主料缺口 × ratio_num / ratio_den)
  ratio_num      INTEGER NOT NULL DEFAULT 1 CHECK (ratio_num > 0),
  ratio_den      INTEGER NOT NULL DEFAULT 1 CHECK (ratio_den > 0),
  scene          TEXT NOT NULL DEFAULT 'sales_out'
                 CHECK (scene IN ('sales_out', 'bom_plan', 'purchase_hint')),
  strategy       TEXT NOT NULL DEFAULT 'proportion'
                 CHECK (strategy IN ('proportion', 'whole_batch', 'manual')),
  cross_warehouse INTEGER NOT NULL DEFAULT 0 CHECK (cross_warehouse IN (0, 1)),
  effective_from TEXT,
  effective_to   TEXT,
  is_active      INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1)),
  remark         TEXT,
  created_by     INTEGER REFERENCES sys_user (id),
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL,
  CHECK (main_item_id <> sub_item_id),
  CHECK (effective_to IS NULL OR effective_from IS NULL OR effective_to >= effective_from)
);
-- 唯一性：包含 NULL 的维度由服务层"先查后写"保证（沿用 stock_alert_rule.assertUnique 先例）
CREATE UNIQUE INDEX uq_item_substitute_scope
  ON item_substitute (main_item_id, sub_item_id, scene,
                      COALESCE(parent_item_id, 0), COALESCE(warehouse_id, 0));
CREATE INDEX idx_item_sub_maine ON item_substitute (main_item_id, is_active);
CREATE INDEX idx_item_sub_sub ON item_substitute (sub_item_id);
```

要点：
- **`parent_item_id` 可空**是"通用替代 vs 特定 BOM 语境替代"的开关（决策 4）。用 `COALESCE(..., 0)` 进唯一索引，规避 SQLite 中 NULL 不参与唯一性判断的坑 —— **这是本项目 `stock_alert_rule` 踩过的同一个坑**，此处用索引表达式一次性解决，比"先查后写"更稳（服务层两道都做）。
- 比例用**整数分子/分母**而非 decimal，直接解决 §1 的整数约束（**已确认，决策 1**）。
- 单向：`(A→B)` 与 `(B→A)` 是两条独立记录。

### 4.3 客户限制：复用 `item_customer_certification`（不新增禁用表）—— **已确认（决策 3）**

- 现有表：`(item_id, customer_id, certified_at, expire_at)`，`UNIQUE (item_id, customer_id)`。
- 语义（拟）：**销售出库场景**下，若用替代料顶替主料，则该替代料必须对该客户存在**未过期**的认证记录；否则跳过并给出原因。
- 关键边界（照抄附件 §4.5 的"特别注意"）：**该限制只作用于"替代"动作**。客户直接下单购买该物料时，认证与否**不影响**正常出库。
- 为什么不加负向禁用表：正向认证是 default-deny、更贴合规，且**表和 UI 都已存在**，只差把校验接上（决策 3）。

### 4.4 待定：`item_substitute_apply`（准入审批单）

仅当你确认需要独立审批单（决策 7）时才建。会复用 `doc_sequence` 单号（需在 `DOC_TYPE_PREFIX` 增加前缀，如 `SA`），字段：`apply_no / main_item_id / sub_item_id / apply_reason / audit_status / audit_user / audit_remark / audit_time`。**不含附件地址字段**（无存储能力）。

## 五、核心模块设计（深度模块）

新建 `packages/server/src/modules/substitute/`：

### 5.1 规划模块的接口

```ts
export type SubstituteScene = 'sales_out' | 'bom_plan' | 'purchase_hint';

export interface SubstitutionRequest {
  mainItemId: number;
  warehouseId: number;
  requiredQty: number;              // 主料需求量（正整数）
  scene: SubstituteScene;
  customerId?: number | null;       // 仅 sales_out 参与客户校验
  parentItemId?: number | null;     // BOM 语境；缺省 = 通用
  strategy?: SubstitutionStrategy;  // 缺省取关系上的策略
  manualItemIds?: number[];         // strategy=manual 时生效
}

export interface SubstitutionAllocation {
  itemId: number;
  itemCode: string;
  quantity: number;      // 实际分配数量（整数）
  isMain: boolean;
  available: number;     // 取数时的物理可用量
  unitCost: number;      // 均价（分），供成本结转参考
}

export type SubstitutionSkipReason =
  | 'no_stock' | 'customer_not_certified' | 'customer_cert_expired'
  | 'relation_inactive' | 'out_of_validity' | 'wrong_warehouse'
  | 'manual_excluded' | 'same_as_main';

export interface SubstitutionPlan {
  requiredQty: number;
  allocations: SubstitutionAllocation[];
  filledQty: number;     // 折算回主料口径的已覆盖量
  gapQty: number;        // 主料口径的剩余缺口
  skipped: { itemId: number; itemCode: string; reason: SubstitutionSkipReason }[];
  warnings: string[];
}

/** 纯计算：只读库，不写任何数据。可注入 db 便于用例直接断言。 */
export function planSubstitution(request: SubstitutionRequest, db?: Db): SubstitutionPlan;
```

### 5.2 接口不变式（属于 interface 的一部分，调用方必须能依赖）

1. **只匹配一层**：绝不递归查询「替代料的替代料」。
2. **不写库**：`planSubstitution` 在同一输入下可重复调用且结果一致（幂等）。
3. **守恒**：`Σ 折算(allocations) + gapQty === requiredQty`（折算口径见 §6.3）。
4. **主料至多一条**且若存在必排首位。
5. **客户端限制只在** `scene === 'sales_out'` 且传入 `customerId` 时生效。
6. **跳过必须给出原因**，不允许静默丢弃（对应附件 §5.5「前端透明」）。
7. **决定性排序**：优先级相同时按 `sub_item_code` 升序，避免同优先级结果不稳定。
8. **整数**：所有数量为整数，取整方向固定且写进 `warnings`（当发生取整时）。
9. 永不抛「库存不足」——库存不足是**结果**（`gapQty`），不是错误；只有非法入参（`main === sub`、比例为 0、需求非正）才抛 400。

### 5.3 为什么它是一个深度模块（而非散在各处）

- **接口小**：一个 `planSubstitution` 调用 → 背后是候选取数（仓覆盖回落 + 场景 + 生效期 + 客户认证）、优先级排序、三种策略分配、整数取整、缺口与跳过原因归集、告警。
- **杠杆**：`shipSales`（替代出库）、IF-9（下游计划）、BOM 展开页建议、采购建议、替代料调用报表 —— 5 个调用方共用一个实现。
- **删除测试**：删掉它，这 5 处各自要重写"过滤 + 排序 + 分配 + 取整 + 原因归集"，复杂度在 5 处重现 ⇒ 它确实在挣自己的位置。
- **接口即测试面**：用内存库直接调 `planSubstitution` 就能覆盖全部边界（认证过期、跨仓、取整、策略），无需起 HTTP。

### 5.4 为什么执行必须与过账同事务，且不新增 `biz_type`

- `stock_transaction.biz_type` 的 CHECK 枚举**无法 ALTER**（SQLite 限制，本项目 `0005` 迁移注释已明确记录同一结论），而它是核心账本，重建表风险不可接受。
- 因此：替代料出库仍写 `biz_type='sale_out'`（数量、成本、仓都正确），**"这是一笔替代"的语义记入 `item_substitute_log`**。
- 好处：账本口径、`as_of` 重算、余额=流水不变量、报表全部无需改动；替代语义可独立查询与追溯。
- 代价：想只看"替代出库流水"需要 join 日志表（可接受，且换来账本零风险）。

## 六、匹配算法

### 6.1 候选取数（SQLite 版，含仓覆盖回落与客户过滤）

```sql
-- 参数：@mainItemId @warehouseId @scene @customerId(可空) @parentItemId(可空) @asOf
SELECT item_id, sub_item_id, priority, ratio_num, ratio_den, strategy, warehouse_id
FROM (
  SELECT s.sub_item_id AS item_id, s.sub_item_id, s.priority, s.ratio_num, s.ratio_den,
         s.strategy, s.warehouse_id,
         ROW_NUMBER() OVER (
           PARTITION BY s.sub_item_id
           ORDER BY CASE WHEN s.warehouse_id = @warehouseId THEN 0 ELSE 1 END,  -- 专属仓优先
                    CASE WHEN s.parent_item_id = @parentItemId THEN 0 ELSE 1 END, -- 父件专属优先
                    s.priority
         ) AS rn
    FROM item_substitute s
   WHERE s.main_item_id = @mainItemId
     AND s.is_active = 1
     AND (s.warehouse_id IS NULL OR s.warehouse_id = @warehouseId)
     AND (s.parent_item_id IS NULL OR s.parent_item_id = @parentItemId)
     AND (s.effective_from IS NULL OR s.effective_from <= @asOf)
     AND (s.effective_to   IS NULL OR s.effective_to   >= @asOf)
     AND s.scene = @scene
     AND (@customerId IS NULL OR NOT EXISTS (      -- 客户认证（仅 sales_out 传值）
           SELECT 1 FROM item_customer_certification c
            WHERE c.item_id = s.sub_item_id
              AND c.customer_id = @customerId
              AND (c.expire_at IS NULL OR c.expire_at >= @asOf)
         ))
) t
WHERE t.rn = 1
ORDER BY t.priority ASC, t.sub_item_id ASC;   -- 决定性排序
```

说明：本项目的"父件专属优先"用 `CASE` 排序实现覆盖回落 —— 同一替代料既有通用规则又有本父件规则时，只取更专属的一条（**已确认（决策 4）**：`parent_item_id` 可为空，通用与父件专属共存，取更专属者）。

### 6.2 三种策略

设 `need` = 主料缺口，`avail(x)` = 该料在该仓的 `available`（八列口径中的 available 桶，**不含冻结/待检**）。

- **`proportion`（按比例混用，默认）**：先用主料可用量（`min(avail(main), need)`），剩余缺口按优先级遍历替代料，`需要量 = ceil(缺口 × ratio_num / ratio_den)`，取 `min(需要量, avail(sub))`；不足则继续下一个。
- **`whole_batch`（整批全量）**：主料 `avail ≥ need` → 全用主料；否则**不混用**，按优先级找第一个 `avail(sub) × ratio_den / ratio_num ≥ need` 的替代料整批覆盖；找不到则返回缺口（并说明"无单一替代料可全额覆盖"）。
- **`manual`（手工指定）**：跳过优先级，按用户给定顺序分配，仅校验库存与合法性（含客户认证），被禁用者直接 400 拒绝（附件 §5.5「手工指定强拦截」）。

### 6.3 整数取整（决策 1、6 的核心）

- 换算：`替代料用量 = ceil(缺口 × ratio_num / ratio_den)`（**向上取整**：宁可多备，不因取整导致缺料）。
- 回算：`折算回主料口径 = floor(替代料实际用量 × ratio_den / ratio_num)`。
- 若发生取整（即非整除），在 `warnings` 中写明 `RM-3003 按比例 2/3 换算：缺口 3 → 分配 2（向上取整，多备 0）` 这类可核对文案。
- `ratio_num/ratio_den` 缺省 1/1 = 1:1 互换，覆盖绝大多数场景。

### 6.4 缺口与原因

- `gapQty > 0` ⇒ 返回缺口并触发既有缺料提示（可对接 `stock_alert_rule`）。
- 若"主料 + 全部候选替代料"仍不足，且存在因**客户认证**被排除的候选，`warnings` 必须明确区分：
  `可用替代料均因客户认证限制被排除，需特批或紧急补货`（附件 §5.5 要求，避免只报"库存不足"）。
- `skipped[]` 全量回传给前端展示。

### 6.5 并发与一致性（替代附件 §5.6）

- **不引入 Redis，也不引入预占表**。理由：本项目库存的唯一写入口是 `postMovement`，且单据服务都是「校验 + 过账同一事务」，SQLite 写事务天然串行化。
- 执行路径必须：**在同一事务内重新 `planSubstitution` 并立即 `postMovement`**，不得把上一次规划结果直接拿来过账（防止两次请求之间的库存漂移）。
- `planSubstitution` 本身**不加锁、不预占**（只读）；因此"看建议"是零副作用的，可安全开放给只读权限角色。
- 若将来要跑多进程，再把事务提升为 `?` + `BEGIN IMMEDIATE`（本项目现在单进程，不做无用功）。

## 七、业务流接入点

### 7.1 销售出库替代（本期唯一"执行"场景）

现状：`shipSales(body)` 按 `sales_order_item.product_id` 逐行过账，预检 `available`。

改造（**加法，不改变原有行为**）：
- `SalesOutboundBody.lines[]` 增加可选项：
  - `substituteItemId?: number`（手工指定替代料）或
  - `allowSubstitute?: boolean`（按规则自动补齐缺口）。
- 服务层在同一事务内：先按原逻辑尝试主料 → 仍缺 → 调 `planSubstitution` → 按分配结果对**替代料**过账（`biz_type='sale_out'`，`bizId` 仍为该销售单）→ 写 `item_substitute_log` → `shipped_qty` 仍累加到**原订单行**。

### 7.2 BOM 展开建议（只读）

- **实施时的调整（与原方案的偏差）**：原方案写的是"给 `explodeBom` 增加可选入参 `withSubstitutes=1`"。实施时改为**不动 `explodeBom`**，由前端在 BOM 展开页对缺口行调用通用的 `GET /api/masterdata/substitutes/plan`（`scene=bom_plan`）来取建议。
  理由：`planSubstitution` 已经是唯一的规划实现，再加一条把同样逻辑塞进 BOM 返回值里的通路，会在两处重复"过滤 + 排序 + 分配 + 取整 + 原因归集"，正好违背本方案 §5.3 的深度模块原则；且完全不动 IF-2b 的返回契约，风险更低。
- 展开结果本身的结构与含义保持不变；BOM 主数据不因替代料而改写。

### 7.3 采购替代建议（只读）

## 九、测试计划（接口即测试面）

直接对 `planSubstitution` 用内存库断言（不需要 HTTP）：

1. **基线**：1:1 替代、主料够 → 全用主料，无替代。
2. **按比例混用**：主料 30/需求 100，替代 1:1、1:2 → 分配与 `gapQty` 守恒（`Σ + gap === need`）。
3. **整数取整**：比例 2/3、缺口 3 → 分配 2（向上取整）且 `warnings` 有可核对文案；回算口径正确。
4. **整批全量**：主料不足且无单一替代料可全额覆盖 → 返回缺口 + 明确原因（不得混用）。
5. **手工指定**：指定顺序生效；指定被客户禁用的替代料 → 400。
6. **客户认证**：未认证 → 跳过且 `skipped.reason='customer_not_certified'`；认证过期 → `customer_cert_expired`；**客户直接下单该物料不受影响**（回归）。
7. **一层不嵌套**：A→B、B→C 同时存在时，匹配 A 只得到 B（不出现 C）。
8. **生效期 / 停用 / 场景 / 仓库**：各自过滤生效，且 `skipped` 原因正确（含 `wrong_warehouse`）。
9. **仓覆盖回落**：同一替代料既有全仓规则又有本仓规则 → 只取更专属的一条（不重复分配）。
10. **决定性排序**：同优先级下按 `sub_item_id` 稳定排序，两次调用结果一致。
11. **不写库**：调用 `planSubstitution` 前后 `stock_transaction` / `stock_balance` / `item_substitute_log` 行数不变。
12. **执行同事务重算**：规划后库存被改，再过账必须按最新库存分配（不得沿用旧规划）。
13. **越界护栏**：`main === sub` 拒绝（schema + 触发器/服务层双保险）；服务端拒绝 0 比例；需求非正拒绝。
14. **账本不变量**：替代出库后「余额 = 流水净额」与既有 `acceptance.test.ts` 断言仍然成立。
15. **权限边界**：无 `sales.outbound.substitute` → 403；只读规划接口（含 IF-9）不需要该权限，无权限者仍可用。

## 十一、待确认决策清单

> 以下 12 项**已于 2026-10-09 全部确认**（均采纳推荐方案），并已回写进本方案正文。

### ✅ 已确认

1. **替代比例与整数数量 → A1 整数分子/分母**。采用 `ratio_num / ratio_den`（如 2/3），换算 `替代料用量 = ceil(缺口 × ratio_num / ratio_den)`，回算 `floor(替代用量 × ratio_den / ratio_num)`；**不改**全系统数量精度（`qty_precision` 仍是独立悬置项）。已记录为 ADR `docs/adr/0001-integer-substitute-ratio.md`。
2. **本期场景范围 → 收敛为「销售出库替代（执行）+ 需求建议（只读）+ 对外接口」**。生产工单领料替代与 MRP 净需求明确留待将来（本项目无此宿主能力）。
3. **客户限制 → 复用 `item_customer_certification` 做正向认证**。不再新增负向禁用表；default-deny，且**只作用于"替代"动作**，客户直接下单购买该物料不受影响。已记录为 ADR `docs/adr/0002-positive-customer-certification.md`。
4. **绑定粒度 → `parent_item_id` 可空**。通用替代（NULL）与父件专属替代共存，同一替代料命中多条时取更专属的一条（唯一索引见 §4.1）。
5. **双向互替 → 本期只做单向 + 一层**。`(A→B)` 与 `(B→A)` 是两条独立记录；不递归查询"替代料的替代料"。
6. **取整方向 → 向上取整**（宁可多备），并在 `warnings` 中给出可核对文案；整除时不产生告警以免噪音。
7. **准入审批单 → 本期不做**。替代关系用 `is_active` + `masterdata.substitute.manage` 权限管控；独立审批单与质检报告附件待通用附件能力具备后再做。
8. **呆滞 90 天 → 做成报表**（不扩展 `stock_alert_rule`）。新增 `GET /api/reports/substitute-usage`，按替代料聚合调用次数、替代数量、最近调用时间与 ≥90 天标记。
9. **对外接口 → IF-8 + IF-9 都加**。IF-8 给替代关系清单，IF-9 给定需求直接返回分配建议（两者均只读无副作用）；沿用 `/api/v1` 既有约定与 `_warnings` 口径说明。
10. **替代料预占/预留 → 不做**。规划接口只读、不预占；执行时在**同一事务内**按最新库存重新规划，避免"规划结果跨请求漂移"与八列口径复杂化。
11. **删除语义 → 硬删除 + `is_active` 停用**（沿用本项目无软删除的先例，唯一性用索引表达式 `COALESCE(...,0)` 防撞键）。
12. **跨仓替代 → 本期只支持同仓**。`cross_warehouse` 字段保留但固定 0、不实现跨仓逻辑。

### 实施中与原方案的偏差（两处，均为刻意）

1. **§7.2 BOM 展开建议**：不改为 `explodeBom` 加 `withSubstitutes` 入参，而是由前端对缺口行调用通用 `/substitutes/plan`。理由见 §7.2 处的说明（避免把同一套规划逻辑复制到第二条通路）。**副作用**：BOM 展开的行结构不含父件信息，故试算时不传 `parentItemId`，绑定到特定父件的替代关系会在跳过列表里显示为 `wrong_parent`——这是刻意的透明行为，不是缺陷。
2. **呆滞报表的口径**：`last_used_at` 与呆滞判定改为**始终按全部历史**（不受报表日期区间影响），日期区间只影响 `substitution_count` / `total_sub_qty`。原实现让区间也参与 `MAX(created_at)`，会导致"任何区间过滤都把区间外用过的替代料显示成从未使用"，90 天口径失真。

### 实施中发现并修复的缺陷（非本方案引入，但由本方案触发）

- **`seed --reset` 会因外键失败**：`db/seed.ts` 的清空清单 `BUSINESS_TABLES` 未包含新增的 `item_substitute` / `item_substitute_log`。这两张表对 `item` 有外键且未声明级联，一旦用户建过替代关系，`pnpm seed --reset` 在删除 `item` 时会报 `FOREIGN KEY constraint failed`。已把两表加入清单（置于 `item` 之前），并在**带替代关系的库副本**上验证重置成功。
- **上线前置条件（必须在文档中显著提示）**：销售出库替代采用正向认证 default-deny，**未配置 `item_customer_certification` 时替代出库完全不可用**（会以 `customer_not_certified` 跳过）。已写入 README「替代料 → ⚠ 上线前置条件：客户认证」。
